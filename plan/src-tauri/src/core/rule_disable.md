# 规则禁用状态重放

## 模块职责

模块负责把「保留但禁用」的规则状态落到 Mihomo 核心：读取当前 runtime 声明的禁用规则原文，解析成核心规则表下标，调用核心 `PATCH /rules/disable` 提交。规则本身照常进入配置和规则表，模块只改变它是否参与匹配。

## 为什么需要重放

- 核心在 reload 配置时重建整张规则表，`extra.disabled` 随之清空，所以禁用状态不能只活在核心运行时。
- 核心接口按下标寻址，而下标会随任意一条规则的增删整体位移，所以持久化侧必须存规则原文，见 `plan/src-tauri/src/enhance/seq.md` 的 `disabled` 字段。
- 两者相加决定了唯一可行的形态：真值存 Profile 的规则增强文件，每次配置 apply 之后由后端把原文解析成当次下标重放一遍。

## 请求与响应

- 目标为核心 IPC：Unix 使用 Unix domain socket，Windows 使用命名管道，路径取自 `dirs::ipc_path()`。
- 方法与路径为 `PATCH /rules/disable`，origin-form URI 配显式 `Host`，等价于 `curl --unix-socket`。
- 请求体是以规则下标字符串为键、布尔为值的 JSON 对象，例如 `{"3":true,"7":true}`；语义为增量 patch，只影响列出的下标，`false` 单条恢复，空对象不清空既有状态。
- 鉴权沿用 clash 配置里的 `secret`，为空时不带 `Authorization`。
- 成功为 2xx 且无响应体；非 2xx 时读取响应体作为错误信息。

## 核心处理流程

- 从 `IRuntime` 取禁用规则原文与已 apply 的配置 Mapping。
- 原文集合为空时直接返回，不发请求：核心刚 reload 完本来就没有任何规则处于禁用，因此「取消禁用」不需要反向调用。
- 按配置 `rules` 序列的位置解析下标，序列下标即核心规则表下标。
- 同一条原文在配置里出现多次时全部禁用，与「这条规则被禁用」的文本语义一致。
- 解析不到下标的原文只记警告并跳过：订阅更新后规则消失属于正常情况。
- 解析结果为空时同样不发请求。

## 副作用与调用时机

- 由 `CoreManager::apply_config` 在 `Config::runtime().apply()` 之后调用，覆盖 reload 成功与 reload 失败改走重启内核两条路径。
- 失败只记警告，不能让禁用状态失败拖垮配置生效；下一次 apply 会重新尝试。
- 模块不写任何配置文件，不改 `IRuntime`，只对核心发一次请求。

## 安全约束与边界

- 只接受来自 runtime 的禁用原文，不接受前端直接传入下标，避免下标在传输期间失效导致误禁用其它规则。
- 前端不直接访问该核心接口，只通过修改规则增强文件间接触发，保证 UI 状态与持久化状态不会分叉。
- 该接口是本 fork 依赖的核心能力，tauri-plugin-mihomo 既未封装也未导出其 IPC 传输层，因此本模块自带最小客户端；上游若补齐接口应整体切换过去。

## 已知限制

- 规则原文不唯一时无法区分具体行，页面层在原文重复时禁止启停。
- 禁用状态跟随 Profile 的规则增强文件，切换 Profile 后由该 Profile 自己的 `disabled` 段决定，不做跨 Profile 继承。
